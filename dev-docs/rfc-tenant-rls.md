## 1. 一段落で

aegra の分離は今「ユーザー単位」で、各クエリに `user_id == user.identity` を書き足すことで守っている。
この RFC は、その外側に「テナント（会社）単位」の分離を足し、**Postgres の行レベルセキュリティ（RLS）で DB 自身に強制させる**。
アプリが WHERE を書き忘れても、DB は別テナントの行を返さない。
DB が見張れない Redis（run のイベント）は、テナントごとの鍵で暗号化して同じ境界を作る。
フラグ `AEGRA_TENANT_RLS_ENABLED` を立てたときだけ動き、立てなければ今と何も変わらない。

```
  リクエスト ──▶ 入口でテナントを1回だけ決める（既定: user.org_id）
                    │ tenant_scope(t)
                    ▼
   ┌─────────── アプリ（今の user_id 条件はそのまま残る）───────────┐
   │ SQLAlchemy の接続  ─ 取り出すたびに role と aegra.tenant_id を設定 │
   │ LangGraph の接続   ─ 同上（checkpoint / store）                    │
   │ Redis のイベント   ─ テナントの鍵で暗号化（AES-256-GCM）            │
   └──────────────────────────────────────────────────────────────┘
                    ▼
   Postgres: RLS ポリシー「tenant_id = 今のテナント」。合わない行は見えない
```

---

## 2. なぜやるか

- 1つの aegra を複数の会社で共有する SaaS では、監査で「会社 A のデータが会社 B に出ない」ことを
  **DB の仕組みとして**説明する必要がある。「全部のクエリに条件を書いた」はコードを全部読まないと確かめられない
- 本家でも、持ち主チェックの書き忘れによる漏えいが続けて見つかっている（GHSA-m98r-6667-4wq7、#424、#431）。
  どれも「WHERE を1か所書き忘れた」「本文の値で行き先を変えられた」種類で、DB 側に最後の壁があれば漏えいにならなかった
- 会社ごとに aegra を1つずつ立てる（DB やスキーマを分ける、#327）方法もあるが、
  会社が100を超えると、接続数・マイグレーション・グラフの読み込みが会社の数だけ増える

---

## 3. 目的にしないこと

- **侵害されたサーバープロセスへの対策。** サーバーは DB のログイン（テーブルの持ち主）と Redis の鍵を持っている。
  グラフのコードも同じプロセスで動くので同じ扱い（#312 が入れば変えられる）
- 運営者からテナントを隠すこと
- 会社の中のユーザー同士の分離。今の `user_id == user.identity` がそのまま担う（§5.1）
- 既にデータがある環境を会社ごとに分けること。全部を1つのテナントに割り当てる移行だけ用意する（§5.6）
- テナントの名簿（レジストリ）と KMS の鍵管理そのもの。本体には差し込み口だけを置く（§5.7）

---

## 4. 今の aegra の分離

| 対象 | 今の守り方 | 漏れたときの結果 |
|---|---|---|
| `thread` / `runs` / `assistant` / `crons` | アプリの WHERE に `user_id == user.identity` | 書き忘れた所から他人の行が読める |
| チェックポイント | `thread_id` で引く。thread の持ち主はメタデータで先に確かめる | 確かめる前に触る経路があれば読める（#431 はこの種類） |
| store | namespace の先頭にユーザーの区切りを Aegra が付ける | 区切りを付け忘れた経路から読める |
| Redis（イベントの再送用リストと pub/sub） | run_id を知っていれば読める | run_id を取り違えると他人のイベントが流れる |

どれも「アプリが正しい」ことに頼っていて、DB や Redis 側には止める仕組みが無い。

---

## 5. 提案

### 5.1 テナントと持ち主は別のもの

- テナント = 「どの会社か」。RLS が守る
- 持ち主 = 「会社の中の誰か」。今の `user_id == user.identity`（将来は #489 の `owner`）が守る。RLS の内側で AND される
- 片方からもう片方を作らない。会社の中での共有の仕方を変えても、会社の境界が広がらないようにするため

### 5.2 スコープ: 誰がテナントを決めるか

処理の単位ごとに「どのテナントとして DB に触るか」を ContextVar に宣言する。
宣言の無いまま DB に触ったら**エラーにする**。既定値で素通しにはしない。

| 宣言 | 使う所 |
|---|---|
| `tenant_scope(tenant_id)` | 入口だけ。HTTP の依存関係、キューから取った run の実行、cron の発火 |
| `system_scope(reason)` | 会社をまたぐ内部の仕事だけ。理由の文字列が必須で、`grep` で一覧できる（起動時の準備、リース切れの回収、スレッド TTL の掃除など8か所） |

- テナントは入口で1回だけ決める。既定は `user.org_id`。別の決め方は `configure_tenant_resolver()` で差し込む
- 入口より下ではテナントの値を引き回さない。`tenant_id` 列は ORM の既定値で今のスコープから埋まる
- テナント ID の形式は `^[A-Za-z0-9_-]{1,64}$` に限る。合わなければ 403

### 5.3 スコープを Postgres に伝える

接続を取り出すたびに、1回の SQL で次の3つを設定する。

```sql
select set_config('role', 'aegra_tenant', true),       -- SET LOCAL ROLE と同じ
       set_config('aegra.tenant_id', $1, true),
       set_config('aegra.system', '', true);
```

- SQLAlchemy 側は、トランザクションが始まるたびに（`after_begin`）。`SET LOCAL` は COMMIT で消えるため
- LangGraph 側（psycopg、autocommit）は、取り出しの全体を1つのトランザクションで包んでから設定する。
  PgBouncer や RDS Proxy のトランザクションモードでも、設定と本体が同じサーバー接続に乗るようにするため
  （包まない作りでは、PgBouncer 1.26 で system の処理が 200回中90回、行を1件も読めなかった）
- 返すときは COMMIT か ROLLBACK で設定が消えるので、次に取り出す処理へ残らない
- 会社をまたぐ処理（system）はロールを切り替えず、`aegra.system = 'on'` を立てる。
  テーブルはすべて `FORCE ROW LEVEL SECURITY` にし、ログインロールにだけ「`aegra.system` が on なら全行」のポリシーを付ける。
  `BYPASSRLS` のロールを使わないのは、マネージドの Postgres ではそれを付けるのにスーパーユーザーが要るため

### 5.4 テーブルとポリシー

| テーブル | ポリシー |
|---|---|
| `thread` / `runs` / `crons` / `checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `store`（意味検索を使うなら `store_vectors` も） | `tenant_id = 今のテナント` で読み書き。列は NOT NULL、既定値は今のテナント |
| `assistant` | 読みは「自分のテナント」か「`aegra.json` から作った共有の行」。書きは自分のテナントだけ。共有の行に変えられないよう CHECK 制約を付ける |
| `assistant_versions` | 親の `assistant` が見えるときだけ見える |
| `thread_ttl` | 権限付与だけ（テナントの中身を持たない） |

- Alembic は `tenant_id` 列（NULL 可）とインデックスを足すだけ。ロール・NOT NULL・ポリシーは
  運用者が `aegra db enable-tenant-rls` で入れる。LangGraph のテーブルは Alembic の後に `setup()` で作られるのと、
  フラグを立てない環境に影響を出さないため
- ポリシーは `NULLIF(current_setting('aegra.tenant_id', true), '')` と比べる。
  一度でも設定した接続は空文字を返すので、`'' = ''` で `tenant_id` の無い行に当たるのを防ぐ
- 会社をまたぐ一意キー: `assistant` の一意インデックスに `tenant_id` を足す。
  `thread` の主キーは全社共通のままで、別の会社が使っている ID で作ろうとしたら 500 ではなく 404 を返す

### 5.5 store と Redis

**store**: 主キー `(prefix, key)` が全社共通なので、2社が同じ namespace とキーを使うと、見えない行とぶつかって書き込みが失敗し、
キーがあることも漏れる。テナントの操作は `("aegra_tenant", tenant_id, *namespace)` に保存し、読むときに外す。
グラフと HTTP API は同じ store を使うので、どちらにも効く。

**Redis**: RLS は Redis に届かないので、run のイベント（再送用リストと pub/sub）をテナントの鍵で暗号化する。

- 平文で残すのは `event_id`（重複除去・Last-Event-ID）と終了フラグだけ。イベントの種類も暗号文に入れる
- AES-256-GCM。AAD は `tenant_id`・`run_id`・`event_id`・鍵の版
- **鍵は読む側の自分のスコープで選ぶ。** Redis や run の行から読んだ値では選ばない。
  別の会社の run_id を渡されても、データではなく `TenantPayloadError` になる
- 鍵は `TenantKeyProvider`。既定はマスター鍵（`AEGRA_TENANT_REDIS_MASTER_KEY`）から HKDF で会社ごとに作る。
  KMS 版は `configure_key_provider()` で差し込む
- 開発用のメモリ上の broker は同じプロセスの中だけなので、手を入れない

### 5.6 有効にする手順

```
1. AEGRA_TENANT_RLS_ENABLED=true（Redis を使うならマスター鍵も）
2. サーバーを1回起動する        → マイグレーションと LangGraph の setup() でテーブルができる
3. aegra db enable-tenant-rls  → ロール・権限・NOT NULL・既定値・ポリシー
```

- 3 は何度実行しても同じ結果になる。意味検索を後から有効にしたら、もう一度実行する
- `tenant_id` の無い行があれば、何も変えずに止まる。`--assign-existing-to T` を付けると、全部をテナント T にしてから進む
- 3 の後でフラグを下ろすと、書き込みが全部失敗する（NOT NULL を埋められない）。戻さない前提にする
- Redis を使っている環境でフラグを切り替えるときは、run を流し切って 600秒（再送用の保持期間）待ってから

### 5.7 本体に入れるものと、外に置くもの

| 本体 | 外（aegra を動かす側のプロジェクト。auth handler と同じ場所） |
|---|---|
| スコープの仕組み、RLS のポリシーと有効化の CLI、store の namespace、Redis の暗号化と HKDF の鍵 | テナントの名簿（その会社が存在して有効か）、KMS の鍵 |
| 差し込み口 `configure_tenant_resolver()` / `configure_key_provider()` | 差し込む中身 |

既定の resolver は `org_id` があって形式が正しいかだけを見る。会社が実在するかは見ない。

## 6. 他の案と、選ばなかった理由

- **会社ごとに DB かスキーマを分ける（#327）**: 分離は強いが、会社の数だけ接続プール・マイグレーション・グラフの読み込みが増える。
  100社では運用が回らない。少数の大口の会社だけを別に立てるのとは両立する
- **アプリの WHERE に `tenant_id` を足すだけ**: 今の `user_id` と同じで、書き忘れがそのまま漏えいになる。
  この RFC が埋めたい穴そのもの
- **会社ごとに Postgres のロールを作る**: 100社なら作れるが、接続プールがロールごとに分かれる。
  1つのロール＋GUC（`aegra.tenant_id`）なら、プールは1つで済む
- **Redis も ACL ユーザーで分ける**: ElastiCache Serverless ではユーザーグループあたり100ユーザーが上限。
  暗号化なら上限が無く、Redis の外にデータが漏れても読めない

## 7. テストの方針

| レベル | 中身 |
|---|---|
| 単体 | スコープの宣言と ContextVar の受け渡し（同期のノードからスレッド経由で store を呼ぶ場合を含む）、resolver の検証、接続ごとの設定、ポリシーの DDL、store の前置き、暗号化（会社が違えば読めない・平文が混じればエラー） |
| 結合 | HTTP の入口でテナントが決まり、決まらなければ 403 |
| E2E（サーバー無し、実 DB） | 2社の行を入れ、相手の行が見えない・書けない。`public` と別スキーマの両方。スーパーユーザーでないテーブル所有者でも FORCE が効く |
| E2E（サーバーあり） | 2社でスレッド・run・store・cron を作り、相手の ID ではすべて 404。Redis の暗号化は本番モード（Redis あり）で |

- 本家の CI に足すのは「フラグを立てた E2E を1ジョブ」。既存のテストはフラグを立てずにそのまま回る
- GHSA-m98r-6667-4wq7・#424・#431 の手口（本文の値で行き先を変える）を、**アプリの持ち主チェックを外した状態でも**
  RLS が止めることをテストに固定したい（§10）

## 8. PR の分け方

フォークの8コミットは、本家に出すなら次の順に組み直す。

1. スコープの仕組み（`core/tenancy/scope.py`）と、全経路の分類（入口で tenant、内部の仕事で system）。フラグを下ろしていれば何もしない
2. Alembic で `tenant_id` 列とインデックス。ORM の既定値
3. 接続ごとの設定（SQLAlchemy と LangGraph のプール）と、有効化の CLI・ポリシー
4. store の namespace の前置き
5. Redis の暗号化と鍵の差し込み口
6. docs（`docs/guides/tenant-isolation.mdx`、環境変数の一覧）と E2E のジョブ

1 だけでも、「スコープの無い DB アクセスを見つける」という点で単独の意味がある。
